# 架构迁移与功能优化总智能体编排指令

## 使用方式

将下方“可复制总指令”完整发送给负责实施的总智能体。总智能体负责检查仓库现状、拆分子智能体、控制并发写入、执行阶段验收，并持续推进到当前获批范围完成。

本指令采用“阶段门控并行”：

- 架构基础迁移是唯一代码关键路径。
- 功能文档可以并行审查和完善。
- 架构基础验收通过前，不得开始大规模功能代码开发。
- 每个后续迁移阶段都根据已经落地的真实接口制定实施计划，不预先假定最终代码结构。

三、总调度原则

采用“阶段门控并行”，不要采用全面并行开发：

1. 架构基础迁移是代码关键路径。
2. 功能文档审查可以与架构迁移并行，但默认只读。
3. 架构验收门通过前，禁止把新大型功能写进旧 game.js 或旧全局系统。
4. 同一时间不得让两个子智能体修改相同文件或高度耦合的文件集合。
5. 子智能体共享工作区时，只有一个代码写入者；其他子智能体执行只读分析、测试设计或审查。
6. 每批改动都必须经过实现者自检和独立审查。
7. 不得使用 git reset --hard、git checkout -- 或其它破坏用户改动的命令。
8. 不得擅自推送远端、创建 PR、合并分支或修改无关文件。

四、子智能体拆分

根据并发槽位自行调度，建议采用以下角色；角色可以复用，但职责不能混淆。

A. 架构基础实施子智能体

职责：

- 严格执行 docs/superpowers/plans/2026-07-26-vue-typescript-foundation.md。
- 按任务和检查框逐项推进。
- 遵循测试驱动：先写失败测试，再做最小实现，再验证通过。
- 负责当前批次获准的代码文件。
- 每个计划任务完成后提交一个范围清晰的 commit。

禁止：

- 提前迁移 Phaser。
- 借迁移之机修改玩法、数值、视觉或文案。
- 让 Vue 直接访问 Game 全局对象。
- 把逐帧实体状态放进 Pinia。
- 删除旧脚本或扩大 LegacyGameEngineAdapter 的公开表面。

B. 功能文档兼容审查子智能体

此角色在第一阶段默认只读，可以与 A 并行。

职责：

- 盘点最近新增的功能优化设计和计划。
- 对每份文档标注其依赖的迁移阶段。
- 将功能映射到 Vue、Pinia、TypeScript domain/service、Phaser 或 Node server。
- 标出仍然要求直接修改 game.js、访问全局变量、依赖内联事件或复制引擎状态的设计。
- 生成“功能设计—目标模块—迁移阶段—阻塞条件”矩阵。
- 给出文档修订建议，但在架构接口实际落地前不要猜测具体实现文件。

禁止：

- 在第一阶段编写功能代码。
- 与架构实施子智能体同时修改 package.json、HTML 入口、src/game/bridge/、测试配置或迁移记录。
- 未经总智能体分配直接修改文档。

C. 验证与回归子智能体

此角色在每个实现批次完成后启动，默认只读；需要补测试时必须先由总智能体分配独占文件。

职责：

- 对照计划检查完成项。
- 运行有针对性的测试和完整回归。
- 检查三个页面入口、旧游戏流程和 server.js 接口。
- 检查 Vue 与旧引擎之间是否只通过 GameEngine 和 LegacyGameEngineAdapter 通信。
- 检查 TypeScript、ESLint、构建和浏览器控制台错误。
- 报告问题的复现命令、根因和影响范围，不直接扩张修改范围。

D. 集成审查子智能体

职责：

- 审查当前批次 diff，而不是泛泛审查整个仓库。
- 检查模块边界、类型安全、订阅清理、错误传播、兼容性和测试覆盖。
- 检查是否误带其他线程或用户的改动。
- 把问题按阻塞、重要、建议三级分类。
- 阻塞问题修复并复验后才能通过阶段门。

E. 后续功能实施子智能体

只有在架构基础验收门通过、功能文档完成架构适配、对应实施计划获批后才能启动。

职责：

- 每次只实施一个边界明确的功能或一个垂直切片。
- 使用新架构模块，不把功能重新塞回旧 game.js。
- 为领域规则写 Vitest，为 Vue UI 写组件测试，为关键流程写 Playwright。
- 保持功能提交与架构提交分离。

五、文件所有权与并发规则

1. 每次派发子任务时必须明确：
   - 可修改文件；
   - 只读文件；
   - 禁止触碰文件；
   - 验证命令；
   - 完成标准。
2. 如果两个任务需要修改相同文件，改为串行。
3. package.json、package-lock.json、Vite/TypeScript/Vitest/ESLint 配置、HTML 入口和 GameEngine 接口属于高冲突文件，只能由当前架构实施者修改。
4. 文档审查者在架构实施期间只输出审查结论；需要落盘时，由总智能体安排独立批次。
5. 每次写入前重新检查 git status，识别其他线程刚产生的提交或工作区改动。
6. 当前已观察到的无关改动可能包括 js/levels/backup/ 和 audit/；以实际 git status 为准，必须保留且不得暂存。

六、执行阶段

阶段 0：预检与行为基线

1. 检查仓库状态、现有提交和正在变化的文档。
2. 阅读权威迁移设计和第一阶段计划。
3. 确认现有 server.js 的 /levels、/save、/reset 接口不能丢失。
4. 运行现有测试，记录迁移前失败项；不要把既有失败伪装成迁移回归。
5. 建立三个页面和关键游戏流程的 Playwright 行为基线。

阶段门 0：

- 基线测试和现有失败记录清楚。
- 没有修改玩法行为。
- 工作区中的无关变更已识别并保持不动。

阶段 1：Vite、Vue 3、TypeScript 基础

严格执行第一阶段实施计划中的六项任务：

1. 记录旧浏览器行为基线。
2. 引入 Vite、TypeScript、Pinia、Vitest、ESLint 和多页面构建。
3. 定义类型化 GameEngine 契约和事件总线。
4. 添加临时 LegacyGameEngineAdapter 和唯一的旧运行时桥。
5. 在游戏、编辑器、展示页挂载独立 Vue/Pinia 根。
6. 补齐迁移记录、README 和完整验证。

Vite 必须继续支持 server.js 提供的编辑器接口。开发与预览环境通过明确代理保留 /levels、/save、/reset，不得用纯静态服务悄悄破坏保存能力。

阶段门 1：

- npm run typecheck 通过。
- npm run lint 通过。
- npm run test:unit 通过。
- npm run test:server 通过。
- npm test 通过。
- npm run build 通过并产生三个 HTML 入口。
- /、/editor.html、/deck.html 可访问。
- /levels、/save、/reset 的兼容路径仍然存在。
- Vue 不直接访问 Game 全局对象。
- 只有 LegacyGameEngineAdapter 可以访问 window.CellQuestLegacy。
- 旧游戏行为、键位、存档和关卡格式没有变化。
- 当前批次提交不包含无关工作区改动。

如果任一条件失败，阶段 1 不得宣告完成，也不得启动功能代码实施。

阶段 2：功能文档架构适配

阶段 1 通过后，重新读取其他线程产生的所有功能优化文档，并基于真实落地接口修订，不依赖迁移前假设。

每份功能文档必须明确：

- 用户行为和验收标准；
- 所属层：Vue、Pinia、domain/service、Phaser、Node server；
- 使用的 GameEngine 命令和事件；
- 数据模型及存档兼容策略；
- 所依赖的迁移阶段；
- 单元、组件、引擎集成和端到端测试；
- 错误处理与回退策略；
- 不允许修改的旧代码范围。

按下列原则分配：

- 页面、菜单、HUD、弹窗、表单：Vue。
- 低频 UI 状态、用户选择、会话展示状态：Pinia。
- 规则、数值、关卡数据、存档迁移：框架无关 TypeScript domain/service。
- 场景、物理、碰撞、动画、逐帧实体状态：Phaser。
- 文件保存和受限本地 API：Node server。
- Vue 与 Phaser/旧引擎通信：GameEngine 命令和类型事件。

阶段门 2：

- 每份功能文档都有明确的目标模块和依赖阶段。
- 不再要求 Vue 直接操作 Canvas、Phaser Scene 或旧 Game 全局。
- 不再建议把逐帧状态复制到 Pinia。
- 功能之间的共享领域模型已识别。
- 每个可实施功能都有独立实施计划或明确等待条件。

阶段 2 后续功能优化执行顺序：

```text

→ 基于真实GameEngine接口重写并实施TypeScript病例运行时
→ AI导演服务端、运行时危机与病例编译器
→ 病例设计器Tasks 8–12
→ 六个官方病例迁移
→ 故事与科普
→ 产品闭环
→ 质量、平衡、可访问性与发布
→ CodeBuddy证据和比赛演示
```

病例设计器Tasks 1–7与AI服务端无冲突部分可以并行；真实试玩必须等待TypeScript病例运行时，AI病例编辑必须等待 `CaseBlueprint`、`CaseCompiler` 和共享 `CaseDraft` 稳定。不得用模拟成功结果绕过这些阶段依赖。

阶段 3：共享领域和 Vue UI

根据总迁移设计为阶段 2、阶段 3 分别编写并执行实施计划：

1. 先提取存档、关卡、成就、牌组、难度、评分等框架无关领域逻辑。
2. 再逐屏迁移菜单、HUD、暂停、结算、图鉴、技能、装备等 Vue UI。
3. 每次只迁移一个可独立验收的模块。
4. 旧 UI 在对应新模块通过回归后才能删除。

阶段 4：Phaser 垂直切片

在全面迁移前先完成一个完整可玩关卡切片，覆盖：

- 资源加载；
- 玩家输入与移动；
- 碰撞和伤害；
- 相机；
- HUD 事件；
- 暂停、死亡、重试、完成；
- 存档与关卡结果；
- Playwright 关键流程。

垂直切片达到行为和手感验收后，才允许扩展到全部实体、关卡和机制。

阶段 5：全量迁移和遗留清理

1. 按实体、系统和关卡批次迁移。
2. 每个批次保留兼容测试。
3. 迁移编辑器和展示页。
4. 确认没有旧代码消费者后再删除 LegacyGameEngineAdapter、window.CellQuestLegacy 和经典脚本。
5. 最后删除旧 game.js，而不是提前删除。

七、测试与验证规则

1. 生产代码遵循 red-green-refactor。
2. 先运行最小相关测试，再运行阶段完整测试。
3. 不得仅凭静态阅读宣称通过。
4. 浏览器测试必须检查 pageerror 和关键控制台错误。
5. 每个迁移模块至少覆盖：
   - 正常路径；
   - 无效输入或缺失数据；
   - 清理/卸载；
   - 旧存档或旧关卡兼容。
6. Phaser 迁移必须额外检查手感、碰撞、帧率和资源清理。
7. 测试失败时先确定根因；不要为了变绿而删除断言或降低既有行为标准。

八、Git 与提交规则

1. 开始和结束每个任务都运行 git status --short。
2. 只暂存当前任务明确列出的文件。
3. 使用路径限定的 git add；提交前检查 git diff --cached --check 和 git diff --cached --stat。
4. 一个提交只表达一个目的。
5. 架构、功能、测试补充和文档修订尽量分开提交。
6. 不修改、撤销或顺带提交其他线程与用户的工作。
7. 未经用户要求不推送远端。
8. 如果工作区发生并发变化，暂停写入，重新确认文件所有权后继续。

九、决策与阻塞处理

可以自行决定：

- 模块内部命名和小范围实现细节；
- 测试拆分；
- 不改变公开行为的局部重构；
- 子智能体调度顺序。

必须停止并请求用户确认：

- 功能文档与迁移总设计发生产品级冲突；
- 需要改变键位、玩法、数值、视觉或存档格式；
- 需要删除旧能力或放弃兼容；
- 需要扩大到未批准的外部服务；
- 两个活跃线程正在修改相同高冲突文件且无法安全串行化。

## 编排设计自检

- 单一总智能体拥有集成责任。
- 架构代码与功能文档允许有限并行。
